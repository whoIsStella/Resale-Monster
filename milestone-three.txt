Read `AGENTS.md`, `README.md`, all database models and repositories, the orchestration service, process supervisor, agent registry and router, CLI commands, migrations, and tests.

Implement Milestone Three: durable worker execution, leases, crash recovery, scheduling, and an authenticated orchestration API.

## Objective

Turn the existing single-job orchestration layer into a reliable multi-worker service that can continuously process jobs, recover from crashes, prevent duplicate execution, reap abandoned work, expose safe API operations, and schedule recurring internal tasks.

Do not add live marketplace mutations.

## Required features

### 1. Worker daemon

Add a long-running worker process that:

* polls for queued jobs
* atomically claims one eligible job
* executes the job through the existing orchestration service
* records completion or failure
* sleeps when no work is available
* shuts down gracefully on SIGTERM or SIGINT
* stops claiming new jobs during shutdown
* waits for or cancels active work according to configuration
* supports configurable polling intervals
* supports configurable worker concurrency
* supports a unique worker identity
* emits structured logs

Add CLI commands similar to:

```bash
goliath worker start
goliath worker status
goliath worker heartbeat
goliath worker reap
```

The worker must not require Codex or Hermes to be installed unless a job needs that agent.

### 2. Durable job leases

Add persistent execution leases.

Each claimed job must record:

* worker ID
* lease owner
* lease token
* lease acquired timestamp
* lease expiration timestamp
* last heartbeat timestamp
* execution attempt number

Requirements:

* only the lease owner may heartbeat or complete the job
* stale lease tokens must be rejected
* expired leases may be reclaimed
* terminal jobs may not be reclaimed
* lease acquisition must be atomic
* job completion must validate the current lease token
* cancellation must remain possible while leased
* lease duration must be configurable
* heartbeat frequency must be configurable
* heartbeat frequency must be shorter than lease duration

Use compare-and-swap updates or database locking.

Document the exact concurrency strategy.

### 3. Crash recovery

Implement recovery for jobs left in `running` state after a worker crash.

Support configurable recovery policies:

* `fail`
* `requeue`
* `retry`

Persist:

* recovery reason
* prior worker ID
* prior lease token hash or safe identifier
* recovery timestamp
* recovery count
* next eligible run time

Never persist raw secrets or sensitive process environment details.

Recovery must append audit events.

Add a reaper that:

1. finds expired running leases
2. verifies they are still expired
3. applies the configured policy
4. records the recovery action
5. prevents concurrent reapers from recovering the same job twice

### 4. Retry policy

Add typed retry configuration.

Support:

* maximum attempts
* fixed delay
* exponential backoff
* maximum delay
* retryable exit codes
* retryable failure categories
* non-retryable task types
* optional jitter
* next eligible execution timestamp

Do not retry:

* explicit cancellation
* invalid submission
* permission rejection
* unsupported agent
* path-validation failure
* forbidden action requests

Tests using jitter must remain deterministic.

### 5. Scheduled jobs

Add internal recurring schedules for orchestration tasks.

Support:

* one-time schedules
* interval schedules
* cron-style schedules
* enabled and disabled schedules
* timezone-aware scheduling
* next-run calculation
* missed-run policy
* maximum catch-up runs
* schedule ownership
* schedule-level task configuration

A schedule should create normal queued jobs rather than executing agents directly.

Persist:

* schedule ID
* name
* task type
* objective template
* requested agent
* workspace
* permissions
* context files
* timing configuration
* enabled status
* last scheduled time
* next scheduled time
* creation and update timestamps

Do not implement marketplace schedules yet.

Initial supported schedule tasks should be limited to safe internal work such as:

* code maintenance
* test execution
* inventory analysis placeholders
* operational audit placeholders

Add CLI commands similar to:

```bash
goliath schedule create
goliath schedule list
goliath schedule show SCHEDULE_ID
goliath schedule enable SCHEDULE_ID
goliath schedule disable SCHEDULE_ID
goliath schedule run-now SCHEDULE_ID
goliath scheduler tick
```

### 6. Worker registry and heartbeats

Persist worker records containing:

* worker ID
* hostname
* process ID
* start time
* last heartbeat
* status
* configured concurrency
* active-job count
* software version
* shutdown timestamp

Worker statuses:

* `starting`
* `healthy`
* `draining`
* `stopped`
* `stale`

Add stale-worker detection.

Do not expose full environment variables, command lines containing secrets, or credentials.

### 7. Authenticated API

Add a FastAPI application for orchestration control.

Endpoints should include:

```text
GET    /health
GET    /ready
GET    /agents
GET    /jobs
POST   /jobs
GET    /jobs/{job_id}
POST   /jobs/{job_id}/cancel
GET    /jobs/{job_id}/audit
GET    /workers
GET    /workers/{worker_id}
GET    /schedules
POST   /schedules
GET    /schedules/{schedule_id}
POST   /schedules/{schedule_id}/enable
POST   /schedules/{schedule_id}/disable
POST   /schedules/{schedule_id}/run-now
```

Requirements:

* typed request and response schemas
* pagination
* filtering by status, agent, task type, and date
* controlled error responses
* no expected-error stack traces
* request IDs
* structured logging
* OpenAPI documentation
* readiness checks for database connectivity
* no agent executable health check on every API request

### 8. Authentication and authorization

Implement API-key authentication suitable for local or private deployment.

Requirements:

* API keys are stored only as secure hashes
* raw keys are displayed only once at creation
* constant-time comparison
* key revocation
* key expiration
* named principals
* last-used timestamp
* scoped permissions

Initial scopes:

* `jobs:read`
* `jobs:write`
* `jobs:cancel`
* `agents:read`
* `workers:read`
* `schedules:read`
* `schedules:write`
* `audit:read`
* `admin`

Do not store raw API keys.

Do not add OAuth or external identity providers yet.

Add CLI commands similar to:

```bash
goliath auth key-create
goliath auth key-list
goliath auth key-revoke KEY_ID
```

### 9. Idempotency

Support idempotency keys for job submission and schedule creation.

Requirements:

* identical repeated requests return the original resource
* conflicting payloads using the same key are rejected
* idempotency records expire according to configuration
* idempotency behavior works across API processes
* idempotency keys are scoped by authenticated principal
* idempotency records do not store secrets
